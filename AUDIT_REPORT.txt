EXECUTIVE SUMMARY
================================================================================
This is a small, clean, well-organized codebase for what it is (no duplicate
files, no duplicate libraries, consistent naming, no circular imports). The
DOMINANT PROBLEM BY AN ENORMOUS MARGIN is Firestore read behavior: virtually
every user interaction re-downloads entire collections from the network, with
zero caching, zero pagination at the database level, and zero realtime
listeners. On a live Firestore project this directly multiplies dollar cost
and load latency. Close behind in urgency is a set of security gaps (missing
security rules, no authentication, unescaped innerHTML/XSS) that should be
treated as equally critical. Everything else (CSS, UI consistency, code
quality) is comparatively minor polish.

5. FIRESTORE PERFORMANCE AUDIT -- HIGHEST PRIORITY
================================================================================

This is the most consequential section. EVERY SINGLE DATA OPERATION in this
app re-downloads entire collections. There is no client-side cache, no
pagination at the query level (Firestore .limit()/.startAfter() is never
used), no .onSnapshot() realtime listener, and no localStorage/sessionStorage
persistence layer despite firebase.firestore().enablePersistence() being
trivially available in the Compat SDK and never called.

CONCRETE READ-AMPLIFICATION FINDINGS:

1. storage.js:20 seedFirestoreIfNeeded()
   Runs db.collection('suppliers').get() unconditionally on EVERY PAGE LOAD,
   all 3 pages.
   Impact: 1 read x every visit, forever.

2. index.js:605-606 initial load
   loadFormDropdowns() calls getSuppliers() + getParts(); loadTableRecords()
   calls getReceivingRecords() + getSuppliers() (again) + getInspectors().
   Impact: Re-fetches getSuppliers() twice in the same page load with no
   reuse.

3. supplier.js:117-178 loadSuppliersList()
   Calls getSuppliers() + getParts() + getReceivingRecords() -- the ENTIRE
   parts collection and entire records collection are downloaded just to
   compute a per-supplier count badge ("3 Parts", "12 Recs").
   Impact: Full 3-collection download, triggered on EVERY KEYSTROKE in the
   supplier search box (no debounce).

4. supplier.js:185-212 selectSupplier()
   Calls getSuppliers() again just to find one supplier by id (client-side
   .find()) -- getSupplierById() already exists in storage.js and does a
   direct single-doc .doc(id).get(), but isn't used here.
   Impact: Downloads whole suppliers collection instead of 1 doc.

5. supplier.js:486-501 loadHistoryTable()
   Calls getReceivingRecords() (ENTIRE records collection, every supplier's
   history, every page load of this tab) + getInspectors(), then filters
   client-side to one supplier in JS.
   Impact: If there are 10,000 records across all suppliers, viewing ONE
   supplier's history downloads all 10,000.

6. supplier.js:999-1007 renderCharts()
   Same pattern -- downloads ALL records for ALL suppliers just to filter to
   one supplier's chart data, re-run on every year/month dropdown change and
   every theme toggle.
   Impact: Full collection re-download per chart re-render.

7. storage.js:166-183 updateSupplier()
   Cascade update: where('supplierId','==',id).get() then loops calling
   .update() ONE DOCUMENT AT A TIME (not batched).
   Impact: N individual writes instead of 1 Firestore WriteBatch/
   BulkWriter.

8. storage.js:185-195 deleteSupplier()
   Same N+1 pattern: fetches all parts for the supplier, then deletes them
   one at a time in a loop.
   Impact: N individual deletes instead of 1 batch.

9. storage.js:324-349 addReceivingRecord()
   Performs getSupplierById() + getInspectorById() as TWO EXTRA READS just
   to denormalize supplierName/inspectorName into the record -- but the
   calling code (index.js) ALREADY HAS the supplier and inspector name
   available in the <select> text at the moment of submission.
   Impact: 2 unnecessary reads per record created, easily avoidable.

10. storage.js:356-380 updateReceivingRecord()
    Same pattern -- 2 extra reads to re-fetch names already known by the
    editing UI.
    Impact: 2 unnecessary reads per record edit.

11. No .limit() anywhere
    getReceivingRecords(), getParts(), getSuppliers(), getComments(),
    getInspectors() all fetch the FULL collection unconditionally.
    Impact: Collection grows unboundedly with usage -- read cost is
    O(all-time data volume) on every single page view, not O(visible page
    size).

ESTIMATED IMPACT:

- Current behavior: A single visit to supplier.html and selecting one
  supplier triggers roughly: 1 (suppliers) + 1 (parts) + 1 (records) [list]
  + 1 (suppliers, redundant) [select] + 1 (records) + 1 (inspectors)
  [history tab] = ~6 full-collection reads, where each "read" actually
  bills Firestore PER-DOCUMENT, not per-query. If "records" has 5,000
  documents, that single click bills ~10,000+ document reads (records
  collection touched twice).

- Typing 5 characters into the supplier search box re-triggers all of the
  above 5 times with no debounce -> could turn a single search into
  50,000+ billed document reads in a few seconds.

PROJECTED SAVINGS FROM CACHING + SCOPED QUERIES:

- Adding a simple in-memory cache for suppliers, inspectors, comments
  (small, low-churn collections) loaded once per page session instead of
  re-fetched on every function call -> ~70-90% reduction in reads for those
  collections.

- Replacing getReceivingRecords() (full collection) + client-side filter
  with db.collection('records').where('supplierId','==',id).get() in
  loadHistoryTable/renderCharts -> reads become O(that supplier's records)
  instead of O(all records ever created) -- with 20 suppliers this is
  roughly a 95% reduction in records-collection reads for that operation.

- Debouncing search inputs (200-300ms) -> 5-10x fewer calls during typing.

- Removing the 2 denormalization reads in addReceivingRecord/
  updateReceivingRecord by passing already-known names from the DOM -> 2
  reads saved per write operation, eliminates ~40% of the reads in the
  hottest write path.

- Removing/conditioning the seed-check read behind a one-time localStorage
  flag -> 1 read saved per page load forever, small but compounds over the
  app's lifetime traffic.

- Loading speed: Each of these changes also directly cuts page-perceived
  latency, since network round-trips to Firestore (not large data volume,
  but round-trip count and document count) are the dominant cost on a
  vanilla SDK with no persistence enabled.

8. SECURITY REVIEW
================================================================================

FINDING: Firebase API key and full project config hardcoded in client-side
  JS, committed to a public GitHub repo
  Location: storage.js:6-13, also README.md:71-78
  Severity: Critical (context-dependent)
  This is EXPECTED/NORMAL for Firebase Web SDK (the API key is not a secret
  in the traditional sense -- it identifies the project, not authorizes
  access) PROVIDED Firestore Security Rules properly restrict access. The
  real critical issue is the next finding.

FINDING: No Firestore Security Rules found anywhere in the repository
  Severity: Critical
  There is no firestore.rules file, and nothing in the codebase suggests any
  rules have been deployed restricting read/write access. If this Firestore
  project is using default rules (deny-all after the default test-mode
  30-day window expires) the app will simply break; if it was ever set to
  test-mode permissive rules (allow read, write: if true) and never
  revisited, ANYONE ON THE INTERNET who finds the API key in this public
  GitHub repo can read, write, or delete every document in every collection
  -- including deleting all supplier/parts/records data. VERIFY IMMEDIATELY
  in the Firebase console.

FINDING: No authentication of any kind
  Severity: Critical
  There is no Firebase Auth integration anywhere in the codebase -- no
  login, no user identity, no firebase.auth(). Combined with the rules gap
  above, this means (depending on current rules config) the entire QC
  database may be world-writable.

FINDING: innerHTML used extensively with unescaped data interpolation --
  XSS risk
  Severity: High
  Dozens of locations build HTML via template literals with ${...}
  interpolation of user-controllable strings directly into innerHTML:
    - index.js:555-565 -- rec.fn, rec.supplierName, rec.detailName,
      rec.comment (all user-entered form text) injected raw into table rows
    - index.js:72 -- comment preset text injected into dropdown <li> raw
    - supplier.js:567-584, 709-726, 152-165 -- same pattern for history
      rows, parts rows, supplier list items
    - settings.js:80-92, 189-201 -- inspector names, comment preset text
    - ui.js:54, 59, 73 -- toast/confirm modal message/title params injected
      raw

  CONCRETELY EXPLOITABLE: if a user types <img src=x onerror=alert(1)> into
  the "Comments" field on the registration form, or names a Supplier/
  Inspector/Part with an HTML/script payload, that payload will execute in
  the browser of EVERY OTHER USER who later views that record in the table,
  history log, or supplier list. This is a textbook stored-XSS
  vulnerability. None of the user-entered fields (F/N, comment, supplier
  name, part name/ID, inspector name) are escaped before being placed into
  the DOM via innerHTML.

FINDING: Client-side validation only, no equivalent server-side enforcement
  Severity: High
  All quantity/range validation (checked <= qty, returned <= checked,
  required fields) lives only in JS (index.js, supplier.js). Without
  Firestore Security Rules enforcing the same invariants server-side,
  anyone who can reach the Firestore REST/SDK API directly (trivial, given
  the exposed config) can write arbitrary invalid data bypassing all client
  checks.

FINDING: No CSV upload validation visible from reviewed files
  Severity: Medium (flag for follow-up)
  supplier.html references a CSV importer per the README but the relevant
  JS for that importer was not present in the files read in this pass --
  worth a dedicated review of the importer code path for injection risks.

FINDING: localStorage usage is benign
  Severity: None (positive finding)
  Only used for "theme" (light/dark) in ui.js:112-119 -- no sensitive data,
  no security concern.

*** This section is the most urgent in the entire report. The combination
of (a) public repo with Firebase config, (b) no visible security rules,
(c) no authentication, and (d) widespread unescaped innerHTML means this
should not be treated as "nice to fix eventually" -- it is a live
data-integrity and XSS exposure that should be addressed before continued
production use, independent of the Firestore cost-optimization work. ***

11. REFACTORING PLAN (ordered by impact, safe/non-breaking)
================================================================================
All steps preserve existing functionality, business logic, and features --
these are internal implementation changes only.

STEP 1 -- Lock down Firestore Security Rules + verify auth posture
  (Critical, do first, near-zero engineering effort)
  Confirm current rules in Firebase console; deploy rules requiring
  authenticated access (or scoped public rules if intentionally public) and
  add basic server-side field validation mirroring the client checks.
  Impact: eliminates the single biggest risk in the app -- unauthorized
  data loss/tampering.

STEP 2 -- Escape all user-controlled innerHTML insertions
  (Critical, ~1-2 hours)
  Introduce one small escapeHtml() helper in ui.js and apply it everywhere
  user-entered strings (comment, fn, supplier/part/inspector names) are
  interpolated into template literals.
  Impact: closes the stored-XSS vector entirely; zero functional/visual
  change for legitimate data.

STEP 3 -- Fix the colspan="8" bug in supplier.js:221-222 to colspan="9".
  (Critical, 1 line, 1 minute.)

STEP 4 -- Introduce a thin in-memory cache layer in storage.js
  for suppliers, inspectors, comments (small, low-churn collections),
  invalidated on writes to those collections.
  Impact: ~70-90% read reduction for those 3 collections across all 3
  pages; faster page loads (fewer round trips); zero behavior change.

STEP 5 -- Replace full-collection-then-filter with scoped .where() queries
  in loadHistoryTable, renderCharts (supplier.js) -- query records by
  supplierId directly instead of downloading everything and filtering in
  JS.
  Impact: read cost becomes proportional to one supplier's data instead of
  the whole records collection; biggest single cost lever in the app,
  scales with data growth.

STEP 6 -- Remove the 2 redundant reads in addReceivingRecord/
  updateReceivingRecord by passing the already-known supplier/inspector
  display name from the calling form code instead of re-fetching.
  Impact: cuts the hottest write-path's read count by ~40%; faster
  perceived submit time.

STEP 7 -- Debounce all search inputs (200-300ms) across index.js and
  supplier.js.
  Impact: 5-10x fewer reads during typing; smoother UI with no flicker
  from out-of-order async resolution.

STEP 8 -- Gate seedFirestoreIfNeeded() behind a one-time localStorage flag
  after first successful confirmation that the DB is non-empty.
  Impact: removes 1 unconditional read per page load, forever, with no
  behavior change for end users.

STEP 9 -- Batch the cascade update/delete writes in updateSupplier/
  deleteSupplier using db.batch().
  Impact: same number of underlying writes (Firestore still bills
  per-document-written), but turns N sequential network round-trips into
  1, meaningfully speeding up supplier rename/delete operations especially
  for suppliers with many parts.

STEP 10 -- Extract the triplicated sort comparator and table-state shape
  into shared helpers in ui.js (UI.sortRecords(arr, column, order),
  UI.createTableState(defaults)).
  Impact: maintainability only, zero runtime/UX change; reduces future
  risk of the three copies drifting apart.

STEP 11 -- Move Google Fonts loading from CSS @import to a
  <link rel="preconnect"> + <link> pair in each HTML <head>.
  Impact: removes one render-blocking request chain hop; modest but
  measurable first-paint improvement.

STEP 12 -- Add pagination to the main Register page's records table
  (reuse the existing renderPagination helper, relocated to ui.js per
  Step 10) instead of hard-capping at 30.
  Impact: restores access to historical records beyond the most recent 30
  -- closes a real functional gap, not just performance.

STEP 13 (optional, larger effort) -- Split supplier.js into cohesive
  modules (supplier-directory.js, parts.js, records-edit.js, charts.js)
  sharing the same DOMContentLoaded init pattern.
  Impact: maintainability only; no behavior change; recommended only
  after Steps 1-12 are stable, since it's the highest-effort, lowest-
  urgency item.
